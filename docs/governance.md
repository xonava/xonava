# Governance

## Compatibility and versioning

The canonical release intentionally retains no obsolete pre-release compatibility surfaces. Future compatibility requires an explicit version decision, documented lifetime, tests, and removal policy; aliases or silent fallback MUST NOT be added ad hoc.

Distinct versions:

- Specification version identifies normative semantics.
- Reference implementation/package version identifies TypeScript release artifacts.
- Durable format version identifies persisted/wire representation.
- Adapter certification version identifies the guarantee suite and source/runtime evidence.

These versions may evolve independently but compatibility claims MUST state which dimensions they cover. Durable writers MUST follow reader-before-writer deployment rules. Public export changes follow the maintained API manifest and package-version policy.

## Certification artifact retention

Certification evidence under `artifacts/framework-conformance` is committed only for the latest
certified release run. Older release runs are removed from the repository, and their history remains
available in version control.

### Policy

- **Kept in the repository:** exactly one release run, the latest certified run, as
  `artifacts/framework-conformance/release-<run-id>/`. Its aggregate manifest and source digests
  must be sufficient to reproduce the certification claim. `ci-artifacts/framework-release-verification.json`
  records the source revision and lockfile digest that the run certified.
- **Not kept in the repository:** earlier release runs. When a new release run is certified, the
  previous one is removed in the same change, after confirming that no governance document or release
  record still points at its run identifier.
- **Git-ignored:** local and ad-hoc runs. Any run whose identifier starts with `local-`
  (`artifacts/framework-conformance/local-*/`) is scratch output that tests regenerate. It is ignored by
  `.gitignore` and must never be committed.
- **Temporary output:** ad-hoc runs should write to an external temporary location where supported
  (for example `FRAMEWORK_DF1_OUTPUT_DIR`). Failed development runs, debug output, and transient
  database or worker files are never retained.

Package `dist` output and build-info are never certification evidence and are always regenerated by
the clean root build.

## Public API manifest

The approved public export surface is recorded in [`governance/public-api-manifest.json`](governance/public-api-manifest.json). Release verification hashes it.
