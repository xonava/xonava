# Running certification

Run `npm run verify:framework-release:local` for the fast local development profile. Its crash checks use one repetition and do not produce release certification.

For release certification, configure `FRAMEWORK_TEST_PG_URL` and `FRAMEWORK_TEST_MYSQL_URL`, then run `npm run verify:framework-release`. The command creates a unique run ID unless `FRAMEWORK_CONFORMANCE_RUN_ID` is supplied, executes all three database providers, runs the DF1 differential suites at release volume with a run-specific seed, repeats every crash failpoint 20 times for every provider, and fails unless the same run produces valid guarantee, crash, and differential evidence. It then emits a source-bound aggregate manifest in `artifacts/framework-conformance/<run-id>/release/`.

`npm run verify:framework-release:baseline` is the underlying one-repetition diagnostic gate. A passing baseline is not a release certification. The internal `verify:framework:cert` step requires the explicit run ID, start timestamp, and initial source digest supplied by the release runner; it validates only that new run and never searches historical evidence. A requested run ID whose artifact directory already exists is rejected. Named V1/MYSQL1 runs use `FRAMEWORK_CONFORMANCE_RUN_ID` and the corresponding certification commands.

## Release profiles and gates

The framework 2.0 profile covers F0–F3. That implementation is framework-owned and independent of consumer applications: neither release profile imports application migrations or application lifecycle code.

The full framework-only profile covers framework builds, package static and export checks, framework-owned migration consistency, core, adapter, and testing typechecks, lint, unit tests, race tests, separate-process crash recovery, and real D1 and PostgreSQL integration and conformance tests. It also regenerates and validates RL1 business-rule, AG1 aggregate, TH1 temporal-history, N1 sequence-numbering, and HT1 HTTP-adapter evidence from the same source snapshot and run identifier.

- `npm run verify:framework-release:local` runs the complete profile that needs no external PostgreSQL service, including the real SQLite execution model used for D1. It is a development gate, not release certification.
- `npm run verify:framework-release` adds the mandatory PostgreSQL integration, conformance, race, and crash suites.
- PostgreSQL certification fails closed unless `FRAMEWORK_TEST_PG_URL` or `DATABASE_URL` identifies a real PostgreSQL server. Absence of PostgreSQL evidence is never treated as proof.
- The `verify:framework:core-purity` gate enforces the dependency-free core contract against both production TypeScript and built JavaScript. It rejects runtime package and Node imports, Node runtime globals, and non-empty `dependencies`, `peerDependencies`, or `optionalDependencies`. The F1 SHA-256 digest is an internal synchronous ECMAScript implementation and does not depend on `node:crypto`, Web Crypto, or a third-party package.
- The version-policy verifier records package versions, the source revision, the lockfile digest, and the public API digest in `ci-artifacts/framework-release-verification.json`. Adapter proof artifacts stay separate under `artifacts/framework-conformance/<run-id>/`.

## Differential certification (DF1)

The release runner runs `npm run verify:framework:df1` after the baseline gate. It reruns the core differential suites and the PostgreSQL, MySQL, and D1 rich/predicate parity suites with `DIFFERENTIAL_REPORT_DIR` set, so the harness records one success line per property, then writes `artifacts/framework-conformance/<run-id>/df1/differential-conformance.json` with the seed, scales, every property with its case count and source call site, totals, replay instructions, and a source manifest. Final certification refuses the run unless that artifact belongs to the same run ID, was recorded after the run started, is proven at release volume, covers every current property call site, and its source digests match the current files.

- **Seed policy.** A release run always uses the seed derived from its run ID (SHA-256 of `framework-df1:<run-id>`), so each release explores new cases and any run is replayable from its run ID or recorded seed. The release runner strips `DIFFERENTIAL_SEED`, `DIFFERENTIAL_RUN`, `DIFFERENTIAL_SCALE`, and `DIFFERENTIAL_REPORT_DIR` from the environment it passes on; DF1 refuses an explicit `DIFFERENTIAL_SEED` inside a release run, and final certification accepts only `seedSource: "run-id"`. A standalone diagnostic run may set `DIFFERENTIAL_SEED` (an unsigned 32-bit integer) to repeat a seed.
- **Volume.** `FRAMEWORK_DIFFERENTIAL_SCALE` multiplies core case counts (default and release minimum 5); `FRAMEWORK_DIFFERENTIAL_DB_SCALE` multiplies real-database case counts (default and release minimum 2). Higher values explore more cases; lower values are accepted only for standalone diagnostic runs, whose evidence final certification refuses.
- **Required properties.** The required set is derived by scanning the suites' `forAll`/`forAllAsync` call sites, so a new property is required automatically. Each reported property is assigned to exactly one call site: a literal name to the literal site with that name, otherwise to the most specific template site that matches it (a template name such as `` `parity (${label})` `` matches any non-empty substitution; two equally specific matches are refused). Every call site needs its own passing properties, so a literal property never stands in for a template site.
- **Baseline.** `scripts/verification/differentialBaseline.json` records every known call site (`file::name`) and how many distinct properties it expanded to. DF1 and final certification refuse a baselined site that no longer exists or that expands to fewer properties than recorded, such as a scenario loop that lost an iteration, even if other properties were added. New sites are accepted (and required) before they are baselined. After a reviewed addition or removal, run `npm run verify:framework:df1 -- --update-baseline` (not allowed inside a release run), review the diff, and rerun the gate.
- **Harness imports.** Only the bare named imports `forAll` and `forAllAsync` of the harness may declare properties, and they must be called directly with a string or template literal name. Aliased (`forAll as check`), namespace, default, dynamic, and re-exported harness imports, and indirect uses such as passing `forAll` as a value, are refused anywhere under `packages/core/src`, `packages/adapters/src`, and `packages/testing`, as is a harness call site outside the DF1 suites.
- **Replaying a failure.** A failing property prints `Replay: DIFFERENTIAL_SEED=<seed> DIFFERENTIAL_RUN=<run>`, and the gate repeats it with the exact suite command. Prefix that command with the two variables to rerun only the failing case, which is shrunk again deterministically; for example `DIFFERENTIAL_SEED=<seed> DIFFERENTIAL_RUN=<run> npm run test -w @xonava/core -- src/__tests__/differential/predicateSemantics.differential.test.ts`. Without `DIFFERENTIAL_RUN`, the same seed and scale rerun the whole suite with identical cases.
- **Standalone runs.** `FRAMEWORK_CONFORMANCE_RUN_ID=<id> npm run verify:framework:df1` needs `FRAMEWORK_TEST_PG_URL` and `FRAMEWORK_TEST_MYSQL_URL`. It first runs the validator's self-test (`npm run test:verification`) and refuses if `DIFFERENTIAL_RUN` is set. A non-release run (including `--update-baseline`) writes its property reports and artifact to `<os tmpdir>/framework-df1-<run-id>` (a random id when `FRAMEWORK_CONFORMANCE_RUN_ID` is unset), never into the repository; set `FRAMEWORK_DF1_OUTPUT_DIR` to choose another directory. Release runs still write `artifacts/framework-conformance/<run-id>/df1/`.

Evidence under `artifacts/framework-conformance/<run-id>/` records guarantee results, source manifests, runtime topology, crash repetitions, and aggregate digests. The aggregate manifest explicitly records that local multi-backend certification does not certify production topology, custom adapters, or offline-unavailable external advisories. Only the latest certified release run is kept in the repository; local runs are git-ignored. See the [retention policy](../governance.md#certification-artifact-retention). A green interface/unit suite is not provider certification.
